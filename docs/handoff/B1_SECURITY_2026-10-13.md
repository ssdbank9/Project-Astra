## Confirmed findings repaired

1. Request framing could pass duplicate headers or consume negative lengths;
   short bodies and non-object JSON were not consistently rejected before
   business dispatch. New guards close invalid requests and return 400;
   genuine inactivity still returns 408.
2. Downloads and framework-generated errors lacked the normal security headers.
   The common response seam now supplies them once, while retaining static/font
   cache behavior and private-response no-store.
3. Internal XML entities expanded beyond the declared ZIP budgets; repeated
   worksheet references multiplied parsing. Parser callbacks and unique resolved
   targets now refuse both. Encrypted/unsupported archives produce workbook
   errors rather than unhandled 500 responses.
4. An in-flight demoted/deactivated App Owner could create accounts or deactivate
   a non-Owner using a stale request snapshot. Sensitive account writes now
   recheck the current active Owner under their write lock.
5. Manager-to-Viewer demotion could still permit task creation/editing between
   the early permission check and write. Task writes now reload current actor
   authority under the lock and preserve Chairman assignment-only permission.
6. New assignees could become inactive or lose project access before write.
   Creation and changed assignments now revalidate eligibility under the lock,
   using the current parent context. Unchanged legacy assignments are retained.
7. Login accepted unrelated Origins and form-compatible JSON content types.
   It now requires `application/json` and a matching Host when Origin is sent.
   A successful cross-site browser exploit was not demonstrated; the new guards
   are verified by server-side tests.

## Aly's decisions during review

- Former importers keep access to their own historical import reports after
  project-access removal. This intentional exception can expose the historical
  report's task details; it was explicitly selected, not overlooked.
- Closed projects must be reopened before anyone creates new tasks, including
  App Owners. This is checked inside the write lock; re-opening authority and
  its existing history remain unchanged.
- Only current active App Owners may change agreed project deadlines through
  either the project date API/screen or linked timeline movement. Managers may
  change project start dates while retaining the agreed deadline. Extensions
  retain the accepted 2FREQ9 Owner/Chairman notification behavior.
- Caddy access logs record real client IPs. No `X-Forwarded-For` trust was added.

Authenticated workplan-template GET downloads intentionally reserve import keys
and write history. Therefore, the accurate CSRF statement is: authenticated
POST/PUT/DELETE business mutations use the session token, with login protected
separately. It would be inaccurate to claim every database write requires CSRF.
